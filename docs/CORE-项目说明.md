## 1. 产品定位

慧财财务系统是一款面向**中小微企业**和**财务代理公司**的纯财务流程管理系统。

采用"**一套底座引擎，双端场景赋能**"的架构：
- **底座（Base）**：科目体系、凭证引擎、会计期间、报表引擎、权限体系等所有企业通用的财务骨架
- **SME 分支**：面向中小微企业的一站式财务闭环（发票、核销、银行流水、资产、报销、预算）
- **Agency 分支**：面向代账公司的多客户批量处理引擎（多账套、批量操作、CRM）

## 2. 目标用户

| 用户类型 | 使用场景 | 核心诉求 |
|---------|---------|---------|
| 中小微企业主 | 自己管账 | 极简操作、自动合规、随时看经营状况 |
| 中小企业财务人员 | 日常记账 | 发票→凭证→报表全流程自动化 |
| 代账公司经理/主管 | 管理团队与客户 | 分配客户给会计、监控服务进度、续费管理、团队效率 |
| 代账公司会计 | 批量处理多家客户 | 批量导入/审核/结账，仅操作分配给自己的客户 |
| 代账公司审核员 | 复核会计工作 | 查看全部客户数据，审核凭证和报表 |
| 代账公司助理 | 票据录入 | 上传发票、录入凭证，仅操作分配给自己的客户 |

## 3. 设计理念

### 3.1 三大铁律

| 铁律 | 说明 | 违反后果 |
|------|------|---------|
| **人是唯一审核主体** | 所有审核/状态变更必须由人主动触发，系统/AI不允许自动审核 | 财务违规，不可接受 |
| **AI 输出 = 建议** | AI 永远不自动应用到财务数据，结果必须人工确认后落库 | 架构走偏 |
| **凭证不可变性** | 已审核/已过账凭证只能红冲修正，不可直接修改 | 数据一致性破坏 |

### 3.2 开发范式

**SDD（Spec-Driven Development）+ BDD（Behavior-Driven Development）+ TDD（Test-Driven Development）三驱动：**

| 环节 | 谁做 | 产出 |
|------|------|------|
| SPEC 编写 | 人（AI辅助） | 四段模板（输入/输出/状态流转/异常处理）+ BDD Given-When-Then |
| 契约定义 | 人+AI | YAML 机器可读契约块 |
| 测试编写 | 人（不可被AI篡改） | 每个 BDD 场景对应一个 @Test |
| 代码实现 | AI | 严格按 SPEC+测试 生成 |
| 代码审查 | 人 | 核心逻辑、并发、金额精度 |

**三步闭环开发流程：**
```
SPEC → 老丁审核 → Plan → 老丁审核 → 开发(微循环) → 测试 → 提交
                                          ↓
                                    Contract-First → TDD Red → Green → Refactor
```

### 3.3 技术哲学

| 原则 | 含义 |
|------|------|
| 确定性/非确定性分离 | 凭证/结账/折旧=Java（确定性），科目推荐/异常检测=Python（非确定性） |
| 单体部署 | 不引入微服务/K8s/Nacos，降低运维复杂度 |
| 核心算法不依赖AI | 折旧计算、核销算法、个税计算都是纯数学公式，AI不介入 |
| 先查现有方案 | 新建任何模块前先检查开源/现有方案是否满足，避免重复造轮子 |

## 6. AI 发展方向

### 6.1 定位

AI 不是慧财的产品，是慧财**数据价值的放大器**。核心假设：

> **慧财已有的财务数据（凭证、流水、发票、往来、报表）是合规 AI 引擎的燃料。不做"另一个记账软件"，做财税合规 AI 引擎，以 API/SaaS 形式嵌入现有代账工作流。**

### 6.2 市场判断

| 竞争格局 | 对我们的启示 |
|---------|------------|
| 金蝶(31年)/用友(38年) 占据头部，品牌+渠道壁垒极高 | 正面硬刚=死路 |
| 基础代账年费从 3,600→2,400 元，价格战见底 | 不能靠低价竞争，必须提供增值服务溢价 |
| 亿企赢砸 200 亿条数据训大模型，畅捷通 6 个 AI 员工 | AI 军备竞赛已开始，但方向偏通用 |
| 金税四期+2026 代账新规，合规是刚需 | **合规是一切客户的核心诉求** |

**三个方向评估：**

| 维度 | A：协作平台 | B：垂直行业深耕 | C：合规 AI 引擎 |
|------|-----------|--------------|--------------|
| 开发成本 | 中 | 高 | **低** |
| 差异化 | 中 | **高** | **高** |
| 市场规模 | **大** | 中 | **大** |
| 巨头威胁 | 中 | **低** | 中 |
| 变现路径 | SaaS 订阅 | SaaS+行业方案 | API+SaaS+按次 |
| AI 利用率 | 低 | 中 | **高** |
| MVP 时间 | 3-4 月 | 6-8 月 | **2-3 月** |

**选择方向 C：合规 AI 引擎。** 理由：成本最低、差异化最强、AI 优势最匹配。

### 6.3 当前 AI 能力盘点

| 能力 | 当前实现 | 是否 AI | 备注 |
|------|---------|---------|------|
| 银行流水 A/B/C 分类 | `classifyType()` 静态路由 | ❌ 硬编码规则 | 最早版本的 AI 替代品，当前是纯 if-else |
| 科目推荐 | AiTaskService + 规则匹配 | ⚠️ 规则引擎 | 未接入模型，基于科目映射表匹配 |
| 异常检测 | AiFeedbackLog 记录+规则 | ⚠️ 规则引擎 | 基础规则检测，无模型打分 |
| 审核建议 | AiTask 骨架 | ⚠️ 骨架 | 有接口定义，无实际逻辑 |
| 核销匹配建议 | 核销工作台 | ⚠️ 规则 | 基于金额+方向匹配，未用 AI |
| P40 AI 服务骨架 | FastAPI 基础框架 | ✅ 架构就绪 | Docker 化、健康检查、Swagger 已配置 |

**关键现实：** 当前的"AI 能力"全部是**硬编码规则或 if-else 路由**，没有接入任何模型。P40 的 FastAPI 骨架是架构就绪但**无实际 AI 推理代码**。这既是差距也是机会——意味着我们不需要重写现有逻辑，而是用 AI 模型**替换**规则引擎。

### 6.4 分阶段规划

#### 阶段 1（当前 → 2026-09）：凭据实性检查 + 异常检测

利用现有数据（审计日志 `t_audit_log`、状态机 `@StatusChangeable`、银行流水分类），实现：

- 凭据实性检查：凭证审核时，AI 预检异常（借贷不平衡、科目异常、金额异常）
- 银行流水异常检测：利用现有分类 + 核销数据，标记异常流水
- 持续监控：对现有审计日志做实时异常告警

**产出：** AI 预审提示 + 审核员确认

#### 阶段 2（2026-09 → 2026-11）：AI 风险评分 + 可交付报告

- 风险评分模型：基于历史数据训练，对每笔业务给出风险等级
- 自动生成可交付报告：PDF 格式，含风险点、修正建议、合规评分
- 代账公司可将其作为增值服务提供给企业主客户

**产出：** 可交付的合规报告（PDF）

#### 阶段 3（2026-11 → 2027-01）：合规规则引擎 + API 输出

- 可配置合规规则：企业可自定义风险阈值、检查项开关
- API 输出：按 REST API 输出合规检查结果，嵌入其他代账系统
- 知识库：金税四期规则、行业标准、新规解读的维护体系

**产出：** API 标准产品 + 规则配置界面

### 6.5 技术路线

```
┌──────────────────────────────────────────────────────────────┐
│                    合规 AI 引擎架构                             │
│                                                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐│
│  │ 规则引擎     │  │ 模型推理     │  │ 报告生成             ││
│  │ (Java, 现有) │  │ (Python AI)  │  │ (Python PDF)         ││
│  │ • 分类路由   │  │ • 异常检测   │  │ • 风险报告           ││
│  │ • 审核状态机 │  │ • 风险评分   │  │ • 合规分析           ││
│  │ • 金额校验   │  │ • 科目推荐   │  │ • 企业主交付版       ││
│  └──────┬───────┘  └──────┬───────┘  └──────────┬───────────┘│
│         │                 │                     │              │
│         └─────────────────┴─────────────────────┘              │
│                            │                                    │
│                    ┌───────┴───────┐                            │
│                    │  数据层       │                            │
│                    │  pgvector     │                            │
│                    │  (现有数据)   │                            │
│                    └───────────────┘                            │
└──────────────────────────────────────────────────────────────┘
```

**关键原则：**
- 确定性逻辑（金额校验、状态机、审核流）继续在 Java 中运行
- 非确定性推理（异常检测、风险评分、科目推荐）在 Python AI 层运行
- 确定性逻辑**不依赖** AI 层——AI 离线也影响不了核心记账流程
- AI 输出永远以"建议"形式呈现，不自动落库

### 6.6 明确不做

| 不做 | 理由 |
|------|------|
| 通用 AI 对话助手（"小慧"） | 与合规方向无关，消耗算力，变现路径不明 |
| 自动审核/自动结账 | 违反铁律（人是唯一审核主体） |
| 训练自己的财税大模型 | 无数据量、无算力、无必要（用现有 API 即可） |
| 银企直连+AI 对账 | 场景尚早，客户需求未验证 |
| 移动端 AI 拍照录入 | 硬件适配成本高，OCR 已成熟直接用现成服务 |

### 6.7 铁律（AI 特殊约束）

| 铁律 | 说明 |
|------|------|
| **AI 输出 = 建议** | AI 永远不自动应用到财务数据，结果必须人工确认后落库 |
| **确定性不依赖 AI** | 核心记账流程（凭证、结账、报表）不因 AI 服务不可用而中断 |
| **AI 不接触原始凭证** | AI 分析基于结构化数据，不直接操作原始发票/银行流水附件 |
| **可解释性** | 每个 AI 输出必须附带原因，不能只给结论不给依据 |
