## 1. P92-A：现金流量表本年累计（本期金额 + 本年累计金额）

### 1.1 现状（代码级事实）

- `ReportServiceImpl.cashFlowStatement(period)` 走 `reportDataMapper.cashFlowData(period)`，**单期间**，按 `flow_type GROUP BY`。
- 返回结构 `Map<String,Object>`，三列：本期金额（无年初/累计对照）。
- **现成范式**：同文件 `trendData(startPeriod, endPeriod)` 已用
  `v.period >= #{startPeriod} AND v.period <= #{endPeriod}` 的期间范围模式（ReportDataMapper.java:140）。
  也就是说**跨期汇总的写法在项目里已有先例**，照抄即可。

### 1.2 方案

1. `ReportDataMapper` 新增 `cashFlowDataYtd(period)`：`v.period >= 年初期间 AND v.period <= period`。
2. `cashFlowStatement` 改为返回 `{ items: [{flowType, currentAmount, ytdAmount}] }`。
3. 前端 `CashFlowView.vue` 加"本年累计金额"列，套用现有 `formatAmount` 千分位。
4. 导出 `exportCashFlow` 同步加第 4 列（hutool merge 列数 +1，注意 P89-D 踩过的单格 merge 守卫 `cols >= 4`）。

### 1.3 验收标准（BDD）

- **P92A-BD1**：Given 某企业 202407–202410 均有现金流凭证 When 查 202410 现金流量表 Then 各行"本年累计金额"= 202401–202410 该类别累计，且"本期金额"不变
- **P92A-BD2**：Given 年初期间即为查询期间 When 渲染 Then 本期金额 == 本年累计金额
- **P92A-BD3**：Given 导出 PDF/Excel When 打开 Then 表头含"本年累计金额"列且列数与前端一致

### 1.4 风险

🟡 **中低**。取数逻辑有现成范式，唯一坑是导出 merge 列数（P89-D 已踩过 `Merged region C2 must contain 2 or more cells`）。

## 2. P92-B：资产负债表分类小计（流动资产/流动负债小计）

### 2.1 现状（代码级事实）

- `ReportServiceImpl.balanceSheet()` **只按科目首位分大类**：
  ```java
  char top = code.charAt(0);
  switch (top) {
      case '1' -> { assets.add(row); totalAssets = totalAssets.add(signed); }
      case '2' -> { liab.add(row);   totalLiab   = totalLiab.add(signed); }
      case '4' -> { equity.add(row); ... }
  }
  ```
  **代码里完全没有流动/非流动维度**——只有"资产/负债/权益"三个大桶。
- `t_subject` 表**无分类字段**：现有字段为 `code / name / parentId / level / direction / isLeaf / auxCalcType / isActive / accountingStandard / remark`，**没有 `category` 或 `accountType`**。

### 2.2 这不是展示层改动

要让"流动资产合计 / 非流动资产合计"成立，必须先有**科目 → 分类**的映射数据。两条路：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **B1 硬编码科目段规则** | 按科目段判定（1001–1599 流动、1601+ 非流动） | 零配置 | 违反科目表可定制；小企业科目可能不连续 |
| **B2 科目表加 `account_type` 列** | 迁移 + seed 更新 + 前端科目维护界面加下拉 | 可扩展，符合会计实务 | 动 migration、动科目维护页、存量数据要回填 |

**我倾向 B2，但这是会计口径决策，不由技术侧拍。**

### 2.3 需要老丁拍板的三个问题

1. **分类粒度**：只做「流动/非流动」二分，还是要「流动/非流动/其他」三分（如长期待摊费用归哪）？
2. **归类依据**：按科目段自动推断，还是科目表人工维护（B1 vs B2）？
3. **小计是否可折叠**：法定报送要求小计行必须常驻（和 P91 利润表骨架同理），那"折叠"这个交互本身要不要做？我建议**不做折叠**——法定报表小计行不可隐藏。

### 2.4 验收标准（待口径确定后补全）

- **P92B-BD1**：Given 流动资产科目合计 500,000 When 查资产负债表 Then 资产区出现"流动资产合计"行且金额正确
- **P92B-BD2**：Given 流动资产合计 + 非流动资产合计 = 资产总计 When 渲染 Then 与表底"资产总计"一致（勾稽校验）
- **P92B-BD3**：Given 未归类科目 When 渲染 Then 归入"其他资产"或报错提示，不静默丢弃

### 2.5 风险

🔴 **高**。动数据库结构 + 动科目维护界面 + 存量科目回填口径 + 法定报送勾稽校验。
**在 B2 口径确定前不应动代码**——否则等于把会计判断写死在代码里，改口径要返工。

## 3. 不做的事（防范围蔓延）

| 项 | 理由 |
|----|------|
| 利润表营业外收支/所得税层级 | 后端 `incomeStatement` **无对应数据字段**（无营业外收入/支出科目聚合），需先建科目与取数，属 P93+ |
| 重分类提示（预付账款贷方余额） | 已有 P90 登记（R-142），不在本次 |
| 资产负债表小计行可折叠 | 法定报送小计行必须常驻，与 P91 同理 |
| 辅助核算展开 | 已有 P90 登记（R-142） |
| 现金流量表间接法 | PRD-018 §6 已裁剪（无数据基础） |
