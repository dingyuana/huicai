# 子 PRD 拆解计划

> **关联**：`CORE-需求分析.md` 总 PRD → 拆解为 12 份子模块 PRD
> **目标**：每份子 PRD 精确描述该模块的完整需求，独立可读，可直接作为研发交付依据

---

## 一、拆解原则

1. **按业务域分割**，对齐现有 DSN 设计文档结构
2. **粒度适中**：每个子 PRD 对应 1 个 DSN + 3-15 个 R 编号
3. **已有不重复**：业务单据管理已 2 份 PRD，不再重写，只做格式对齐
4. **已完成模块写概要**：已实现的功能写「现状+验收标准」，不写详细交互
5. **待建模块写详细**：工资薪酬、Agency 批量操作、AI Agent 写完整需求

## 三、各子 PRD 内容模板

每份子 PRD 统一结构（避免再出现 V2.0 PRD 那种过度设计问题）：

```markdown
# {模块名} PRD

> **编号**：HUICAI-PRD-{序号}
> **版本**：V1.0 | **日期**：2026-08-19
> **关联总 PRD：`(../CORE-需求分析.md)` 
> **关联设计**：DSN-{xxx}.md

## 1. 模块定位
- 一句话说明该模块做什么、不做什么
- 边界：明确不做的功能

## 2. 功能清单
| 编号 | 功能点 | 优先级 | 当前状态 | 验收标准 |
|------|--------|--------|---------|---------|
| {模块}-001 | 功能描述 | P0 | ✅ 已完成 / ⚠️ 部分 / ❌ 待建 | BDD Given-When-Then |

## 3. 状态流转（如有）
- 状态机图
- 合法/非法转换

## 4. 核心业务规则
- 编号规则
- 校验规则
- 权限规则

## 5. 验收标准
- 每个功能点的 BDD 场景
- 测试通过条件

## 6. 不做的事
- 明确列出现阶段不做的功能，避免 PRD 膨胀
```
