# huicai 项目开发规范 — 差距检测与设计-实施同步

**生效日期**: 2026-06-24
**起草依据**: P28 漂移修复 + P29 死列清理暴露的设计-实施差距（详见 docs/tasks/P28.../P29...）
**适用范围**: huicai 全项目（Java 后端 + 前端 + migration + SPEC）
**强制级别**: **硬约束**——任何违反本规范提交的代码/Hermes 任务，**必须先改正再合并**

## 0. 规范目的

解决 huicai 项目已发生的 4 类典型问题：

1. **设计文档与实施代码长期错位**（P26 SPEC §11 "V50 种子模板"是虚构、实际分散在 V23/V40/V42）
2. **PG schema 漂移**（V50 文件从未在 git 存在、PG history 已有记录 1 周才被发现）
3. **死列（无引用的表字段）**（t_business_doc.customer_name/supplier_name 长期无 Java 代码使用）
4. **SPEC 阶段未标记**（P26 §0 表格第 14-16 行写得像全要做，实际是 P2 阶段搁置——读者无法分辨）

**核心原则**：**PG 现网状态 = 唯一事实源**。设计文档必须随时与 PG 对齐，否则视为过期。

## 1. 三方对照规则（核心硬约束）

任何**新增字段、新增表、新增 migration** 必须满足以下三方对照全部通过：

### 1.1 三方对照清单

```
□ 1. PG 层：表/字段存在
      SELECT column_name FROM information_schema.columns WHERE table_name = 't_xxx';
□ 2. Java Entity 层：字段定义存在
      grep "private.*xxx" backend/src/main/java/.../XxxEntity.java
□ 3. Java 调用层：业务代码引用
      grep -r "\.getXxx\|setXxx" backend/src/main/java/ | grep -v Entity.java
□ 4. MyBatis XML 层：列引用
      grep -r "xxx" backend/src/main/resources/mapper/
□ 5. 测试层：测试代码引用（按需）
      grep -r "xxx" backend/src/test/
```

**判定规则**：

| PG | Entity | 调用方 | XML | 判定 | 行动 |
|---|---|---|---|---|---|
| ✅ | ✅ | ✅ | ✅ | 真活字段 | 正常使用 |
| ✅ | ❌ | ❌ | ❌ | 死列 | 立即清理（删字段 + 删 V__ migration） |
| ❌ | ✅ | ✅ | ✅ | 影子字段 | 必须补 V__ migration 落地 PG |
| ✅ | ✅ | ❌ | ❌ | Entity 死代码 | 清理 Entity 字段 + 重跑测试 |
| ✅ | ✅ | ✅ | ❌ | MyBatis 漏配 | 补 XML 或调整 SQL |

**任一项不通过 = 该字段/表设计存在差距，禁止直接 commit**。

### 1.2 三方对照的强制时机

| 时机 | 必须做 | 输出 |
|---|---|---|
| 起草 SPEC 时 | 跑 §1.1 第 1、2 项 | 确认"应增加字段"在 PG/Entity 现状下确实缺失 |
| 实施 migration 前 | 跑 §1.1 全部 5 项 | 确认新字段确实有调用方（避免新增死列） |
| commit 前 | 跑 §1.1 全部 5 项 | 确认提交后字段仍是真活 |
| SPEC 完成后归档 | 跑 §1.1 全部 5 项 | 确认 SPEC 描述与实施一致 |

### 1.3 三方对照不通过的处置

**不通过 ≠ 立刻 commit**。必须：

1. 在工单里明确记录"对照不通过项 + 处置方式"
2. 三选一：
   - 修代码让对照通过（最常见）
   - 修 SPEC 让期望对齐实际
   - 补 migration 让 PG 对齐代码
3. **禁止**"先 commit 再说"——这是 V50 漂移的成因

## 2. SPEC 阶段标记强制规范

### 2.1 阶段标记 4 种状态

任何 SPEC 的"改动清单总览"表格**必须**在每行加"阶段"列，使用以下 4 种标记：

| 标记 | 含义 | 验收要求 |
|---|---|---|
| ✅ | 当前阶段已实施 | mvn test 通过 + commit 已 merge |
| ⏸ | 后续阶段，未实施 | 必须在 §N 单独章节列"暂搁置原因 + 触发重新评估条件" |
| 🚫 | 已决定不实施 | 必须在 §N 整章加废弃说明 + 引用取消决策的 commit |
| 🔄 | 实施中（部分完成） | 必须在 §N 列"已完成子项 + 未完成子项" |

### 2.2 表格模板

```markdown
| # | 改动 | 文件 | 风险 | 阶段 |
|---|------|------|------|------|
| 1 | XXX | `Xxx.java` | 🟡 中 | ✅ P0 |
| 2 | YYY | `Yyy.java` | ✅ 低 | ⏸ P2 |
| 3 | ZZZ | `Zzz.sql` | 🟡 中 | 🚫 已废 2026-06-24 P28 |
| 4 | WWW | `Www.java` | 🟡 中 | 🔄 部分完成 |
```

### 2.3 阶段标记的合并规约

- ✅ 和 ⏸ 必须在表格中**视觉上区分**（emoji + 缩进）
- ⏸ 章节必须在 SPEC 末尾 §N "未实施章节"集中列一遍（防止读者漏看）
- 🚫 章节必须保留原内容（不删除）作为历史参考，但标题加废弃说明

## 3. Migration 漂移检测规范

### 3.1 漂移的 3 种类型

| 类型 | 表现 | 根因 |
|---|---|---|
| A. 文件缺失 | `flyway_schema_history` 有 V__ 记录，git 无文件 | 手工 psql + 手动塞 history（V50 类型） |
| B. 文件未提交 | 临时 mvn 跑过 V__，但文件未 `git add` | 实施者忘 commit 文件 |
| C. 顺序错乱 | V45 删除但 V46 注释未更新 | 历史 P21-a-1 bug（详见 V46 注释） |

### 3.2 CI 必跑检测（每个 PR）

**`mvn flyway:info` 状态检查**：

```bash
mvn flyway:info -Dflyway.url=$DB_URL -Dflyway.user=$DB_USER -Dflyway.password=$DB_PWD \
  -Dflyway.locations=filesystem:src/main/resources/db/migration
```

**期望输出**：
- 全部 migration 状态 = `Future` 或 `Success`
- **禁止出现**：`Pending`（待跑但未跑）/ `Outdated`（已跑但文件被改）/ `Missing`（已跑但文件被删）

**`Missing` = 必须立即修复的 P0 bug**——直接阻断 PR merge。

### 3.3 临时操作 24 小时回流规则

**任何**以下操作必须在 24 小时内补成正式 migration：

- `psql -c "ALTER TABLE..."`
- `psql -c "INSERT INTO..."`
- 手动 `INSERT INTO flyway_schema_history ...`
- 任何绕过 `mvn flyway:migrate` 的 schema 变更

**24 小时未回流** = 必须建 P__ 工单说明"为什么没回流 + 何时回流"——**禁止**让临时操作长期存活。

### 3.4 migration 文件命名规范

- 编号递增（V46 之后是 V47，不允许跳号）
- 删除 migration 不允许（V45 跳号是历史特例，必须有 V46 注释说明）
- 文件名必须能反映内容（V50__add_business_doc_customer_supplier_name.sql）

## 4. 任务书验收清单规范

### 4.1 必须包含的验收项

每个 P__ 工单的"验证清单"（§2 验证清单）必须包含：

```markdown
- [ ] mvn test 通过（具体数字预期）
- [ ] 改动文件清单与预期一致
- [ ] 三方对照全部通过（见 §1 硬约束）
- [ ] SPEC 同步项（新增 §/修改 §/标废弃 §）— 列出章节号
- [ ] commit message 符合 §29 规则
- [ ] push 成功
- [ ] 工作树干净
```

### 4.2 SPEC 同步的强制要求

**实施完成后**，如果工单涉及 SPEC 改动，**必须**在 commit 前完成：

- 新增 SPEC 章节 → 直接在文档加 §N.N
- 修改 SPEC 章节 → 用 `patch` 工具精确定位修改
- 标废弃 SPEC 章节 → 加 🚫 标记 + 引用取消决策的 commit

**禁止**"代码改了、SPEC 没改"的状态长期存在——这是 P26 §11 虚构的成因。

### 4.3 任务书与 SPEC 的引用关系

每个 P__ 工单必须在 §0 列出：

```markdown
## 0. 关联 SPEC
- 改动 SPEC: docs/specs/P##-xxx.md §N.N（具体章节）
- 废弃章节: docs/specs/P##-xxx.md §N（标 🚫）
```

任务书 commit 时**必须**和 SPEC 改动在同一个 commit（或同一 PR）——禁止拆分到不同 commit 增加追溯成本。

## 5. 季度审计规范

### 5.1 审计频次

**每季度末**（3/6/9/12 月最后一周）跑一次全项目差距审计，由项目负责人执行。

### 5.2 审计脚本（最小集）

```bash
# 1. flyway 漂移检测
mvn flyway:info -Dflyway.url=$DB_URL -Dflyway.user=$DB_USER -Dflyway.password=$DB_PWD \
  -Dflyway.locations=filesystem:src/main/resources/db/migration

# 2. 死列检测（候选）
PGPASSWORD=$DB_PWD psql -h $DB_HOST -U $DB_USER -d $DB_NAME <<EOF
SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name LIKE 't_%'
ORDER BY table_name, ordinal_position;
EOF
# → 人工对照 Entity + 调用方清单

# 3. SPEC 阶段标记审计
grep -L "✅\|⏸\|🚫\|🔄" docs/specs/P*.md
# → 输出缺少阶段标记的 SPEC，必须补齐
```

### 5.3 审计输出

审计结果必须在 `docs/audit/` 下创建 `<YYYY-MM-DD>-差距审计.md`，包含：

- 漂移项数量 + 列表
- 死列候选数量 + 列表
- 缺阶段标记的 SPEC 列表
- 处置建议（建 P__ 工单 / 当场修 / 接受现状）
