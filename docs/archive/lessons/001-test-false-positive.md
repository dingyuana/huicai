# 复盘：编号关联体系测试假阳性

## 事件

2026-06-28 至 2026-06-29，huicai 项目编号关联体系（V64 Migration）开发过程中，出现"测试全部通过但功能实际断裂"的情况。

## 现象

- V64 Migration 落地后，59/59 测试全部通过
- 测试覆盖：Mapper 字段测试、Controller 接口测试、E2E 链路测试、Job 一致性检查
- 但实际运行中，发票→应收单→凭证的编号链路并未贯通

## 根因

### 1. 需求理解偏差

设计文档 `NUMBERING_ASSOCIATION.md` 要求的是**跨实体编号链路贯通**（发票号↔应收单号↔凭证号互相可追溯），但实际实现理解成了**给每个实体加编号字段**。

- 设计意图：A 实体能查到 B 实体的编号，B 能查 A
- 实际实现：A 有字段 `no_a`，B 有字段 `no_b`，但 A 的 `no_b` 是空的，B 的 `no_a` 也是空的

### 2. 测试用例设计缺陷

测试只覆盖了"单个实体的编号字段能存能查"，没有覆盖"跨实体链路贯通"：

| 测试类型 | 测试内容 | 是否覆盖链路 |
|----------|----------|-------------|
| Mapper 字段测试 | Entity 有 `voucherNo` 字段，能 INSERT/SELECT | ❌ 只测单个实体 |
| Controller 接口测试 | 给定 ID 能查到 `voucherNo` | ❌ 没有测试"通过发票号查凭证号" |
| E2E 链路测试 | Mock 数据手动设好编号 | ❌ 编号是预设的，不是链路生成的 |
| Job 一致性检查 | 检查字段不为 NULL | ❌ 只检查单个字段存在性 |

**核心问题：所有测试的编号数据都是"静态预设"的，没有一个是"动态生成并贯穿链路"的。**

### 3. 实现遗漏

以下关键逻辑在实现中被遗漏：

| 遗漏点 | 预期行为 | 实际行为 |
|--------|----------|----------|
| `OutputInvoiceStateMachineServiceImpl.createReceivable()` | 生成应收单编号并回写到发票 | 只创建了应收单，没编号，没回写 |
| `ReceivableEntity` | 有 `receivableNo` 字段 | 字段不存在，直到 V65 才补 |
| `OutputInvoiceEntity` | 有 `receivableId` + `receivableNo` | 字段不存在，直到 V65 才补 |
| 分页查询接口 | 支持按 docNo/invoiceNo/voucherNo 搜索 | 只支持按 ID/状态/期间搜索 |

## 修复

2026-06-29 commit `3da85f2` 补全：

1. `ReceivableEntity` 新增 `receivableNo` 字段
2. `OutputInvoiceEntity` 新增 `receivableId` + `receivableNo`

4. 状态机回写发票的应收单 ID 和编号（双向追溯）

## 教训

### 设计层面

1. **设计文档 ≠ 字段清单**。设计文档描述的是业务行为和链路，不是简单的字段加减。理解需求时必须区分"数据结构"和"业务流程"。
2. **跨实体关系必须用链路测试验证**。单个实体的 CRUD 测试永远无法发现链路断裂问题。

### 测试层面

3. **测试数据不能全是预设值**。至少有一部分测试数据应该是通过真实业务流程"自然产生"的，这样才能验证链路贯通。
4. **E2E 测试必须模拟真实用户操作路径**。Mock 数据手动设编号等于绕过了真正的业务逻辑。

### 流程层面

5. **设计评审时必须追问"用户怎么用"**。如果设计评审时有人问"用户通过发票号怎么找到对应的凭证号？"，这个断裂会被立刻发现。
6. **实现完成后必须做一次"用户视角"的走查**。不是看代码有没有加字段，而是走一遍完整的业务流程。
