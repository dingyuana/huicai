# Spec 规范报告

## 1. 项目概述与设计理念

### 1.1 项目概述

本项目旨在打造一款对标用友 BIP 与金蝶星空底层架构的“AI 原生多账套智能财务协同平台”。平台采用 SDD（规范驱动开发）+ TDD（测试驱动开发）的单人 AI 协同编程范式，将复杂的财务系统解耦为 26 个独立且高内聚的 Spec（规范）。通过严格的契约约束与 AI 辅助编码，确保在单人开发模式下，系统具备企业级财务软件的高并发、高可用与高合规特性。

### 1.2 设计理念

- **规范驱动 (Spec-Driven)**：所有功能开发前必须完成 Spec 定义，明确输入、输出、状态流转与异常处理。Spec 即代码的“宪法”，AI 仅作为 Spec 的执行器。
- **测试前置 (TDD First)**：在编写任何业务逻辑前，先基于 Spec 编写单元测试与集成测试。AI 生成的代码必须通过 100% 的测试用例方可合并。
- **AI 原生融合**：摒弃传统“外挂式 AI”架构，将 AI 能力（票据识别、科目推荐、自然语言查账）作为一等公民融入核心业务链路，通过规则引擎兜底确保财务严谨性。
- **分层解耦与拓扑隔离**：将 26 个 Spec 划分为七大层级，严格遵循自下而上的依赖拓扑，禁止跨层反向依赖，确保基础设施与核算底座的绝对稳定。

## 2. S-00 规范：全局 API 契约、DTO 命名与统一错误码

### 2.1 规范概述 (Overview)

本规范是整个 AI 原生财务协同平台的“通用语言”。它定义了前后端交互的 RESTful 标准、数据传输对象（DTO）的命名与分层原则，以及全局统一的异常响应结构。所有后续 Spec（S-01 至 S-27）的接口设计与代码生成，**必须严格遵循此规范，禁止任何形式的自定义或偏离**。

### 2.2 RESTful API 设计契约 (API Contract)

- **URL 命名**：采用全小写、中划线分隔（Kebab-case）。资源名称使用复数名词。
    - *正确示例*：`/api/v1/account-subjects`, `/api/v1/vouchers`
    - *错误示例*：`/api/v1/getAccountSubject`, `/api/v1/account_subjects`
- **HTTP 动词语义**：
    - `GET`：获取资源（支持分页参数 `?page=1&size=20`）。
    - `POST`：创建资源。
    - `PUT`：全量更新资源。
    - `PATCH`：局部更新资源（如凭证状态变更）。
    - `DELETE`：删除资源。
- **版本控制**：所有 API 必须包含版本号，统一前缀为 `/api/v1/`。

### 2.3 数据传输对象 (DTO) 分层与命名规范

为隔离业务实体与外部接口，严禁将数据库 Entity 直接暴露给前端。必须采用以下分层：

- **Command (创建/更新指令)**：用于接收前端 POST/PUT 请求。
    - *命名*：`Create[Resource]Command`, `Update[Resource]Command`
    - *示例*：`CreateVoucherCommand`
- **Query (查询条件)**：用于接收前端 GET 请求的复杂查询参数。
    - *命名*：`[Resource]Query`
    - *示例*：`VoucherPageQuery`
- **VO (视图对象)**：用于向前端返回展示数据。
    - *命名*：`[Resource]VO`
    - *示例*：`VoucherDetailVO`
- **字段命名**：所有 JSON 字段严格采用 **小驼峰命名法 (camelCase)**。金额字段统一后缀 `_amount`（如 `debitAmount`）。

### 2.4 全局统一响应结构 (Unified Response Envelope)

无论请求成功或失败，HTTP 状态码为 200 时，Body 必须严格遵循以下 JSON 结构：

```json
{
  "code": 200,           // 业务状态码 (200表示成功，其他为具体业务异常)
  "message": "success",  // 提示信息
  "data": {},            // 业务数据 (失败时可为 null)
  "traceId": "uuid-v4"   // 链路追踪ID，用于排查问题
}
```

> **注意**：分页查询的 `data` 必须包含：`list` (数据集合), `total` (总条数), `page` (当前页), `size` (每页条数)。
> 

### 2.5 全局错误码字典 (Error Code Dictionary)

错误码采用 **5位整数**，按业务域分段，严禁使用魔法数字：

| 错误码段 | 业务域 | 示例与说明 |
| --- | --- | --- |
| `20000 - 20099` | 系统级异常 | `20001`: 参数校验失败; `20002`: 未授权/Token过期; `20003`: 跨租户越权访问 |
| `20100 - 20199` | 业财底座(科目/凭证) | `20101`: 借贷不平衡; `20102`: 非末级科目禁止记账; `20103`: 会计期间已锁定 |
| `20200 - 20299` | 税务与发票 | `20201`: 发票验真失败; `20202`: 红冲条件不满足 |
| `20300 - 20399` | 资金与核销 | `20301`: 核销金额超出未核销余额; `20302`: 银企直连超时 |
| `20400 - 20499` | AI 智能层 | `20401`: AI 识别置信度过低; `20402`: AI 服务降级/超时 |

### 2.6 行为契约与测试规范 (BDD for S-00)

*以下为 AI 生成全局拦截器与异常处理器必须通过的测试用例：*

**场景 1：参数校验失败自动包装**

- **Given** 前端提交了一个缺少必填项 `voucherDate` 的 `CreateVoucherCommand`。
- **When** 请求进入 Controller 层。
- **Then** 系统拦截异常，返回 HTTP 200，Body 为 `{"code": 20001, "message": "凭证日期不能为空", "data": null, "traceId": "xxx"}`。

**场景 2：业务异常统一捕获**

- **Given** Service 层抛出了自定义业务异常 `TenantViolationException`。
- **When** 全局异常处理器捕获该异常。
- **Then** 返回 HTTP 200，Body 为 `{"code": 20003, "message": "禁止跨租户操作", "data": null, "traceId": "xxx"}`。

**场景 3：AI 降级兜底响应**

- **Given** 调用 AI 科目推荐服务超时（>3秒）。
- **When** 触发熔断降级机制。
- **Then** 返回 HTTP 200，Body 为 `{"code": 20402, "message": "AI 推荐服务繁忙，请手动选择科目", "data": null, "traceId": "xxx"}`。

为确保开发顺序的正确性，各 Spec 必须严格遵循以下依赖拓扑。基础设施层为全局贯穿依赖，业务层与 AI 层严格依赖核算底座。

```

[外部依赖] 银行 API / 乐企平台 / OCR 服务 / 税控设备
```

## 5. Loop Engineering 执行策略

在单人 AI 协同编程范式下，采用“规范-测试-实现-验证”的闭环工程 (Loop Engineering) 策略：

1. **Spec 定义与评审**：针对当前迭代目标，使用 AI 辅助完善 Spec 文档。确保输入输出边界清晰，异常分支穷尽。
2. **测试用例生成 (TDD)**：基于 Spec 要求，让 AI 生成单元测试与集成测试代码。此时运行测试应全部失败 (Red)。
3. **AI 代码生成 (SDD)**：将 Spec 与失败的测试用例作为 Prompt 输入给 AI，要求其生成符合规范的实现代码。
4. **自动化验证与修复**：运行测试。若测试失败，将错误日志反馈给 AI 进行自我修复；若测试通过，进入代码审查阶段。
5. **规则兜底与人工抽检**：对于 S-08、S-12 等极高复杂度 Spec，AI 生成代码后必须经过 Drools 规则引擎校验或人工核心逻辑抽检，确保财务数据的绝对准确。
6. **文档与 Spec 同步**：代码合并后，自动更新 API 文档，并回溯检查 Spec 是否需要根据实际实现进行微调。

### 6.2 资源规划与开发建议

- **极高复杂度模块（S-07, S-08, S-12, S-24）**：此类模块涉及核心财务算法与复杂状态机。建议采用“小步快跑”策略，将大 Spec 拆分为多个子任务。AI 生成代码后，必须引入独立的验证脚本进行边界值与并发测试。
- **高复杂度模块**：占据系统主体，建议按照依赖拓扑图严格串行开发。在开发 S-08（凭证引擎）前，务必确保 S-04 至 S-07 的测试覆盖率达到 95% 以上。
- **AI 模块（S-08-AI, S-08-BI, S-09-NL）**：AI 具有不确定性，开发重点应放在“规则兜底”与“降级策略”上。建议先完成对应业务模块（如 S-06, S-08, S-09）的 100% 自动化测试，再开发 AI 增强层。
- **基础设施层（S-00, S-01~S-03）**：作为全局依赖，建议在项目第 1 周优先完成并冻结接口。后续迭代中如需修改，必须触发全量回归测试。
