## 1. 调研目标

- **目标领域：** 银行流水自动分类（Bank Statement Categorization）
- **重点关注维度：** 分类规则引擎、AI/ML 模型、用户交互模式、与业务单据的映射关系、异常处理
- **排除项：** 不关注银企直连/流水导入的技术细节，仅关注分类逻辑
- **自身产品背景：** 慧财（huicai）已有银行流水模块（导入、展示），需开发智能分类功能，将流水条目自动匹配到业务类型（销售收入、采购付款、费用报销等），并生成对应业务单据

## 4. 关键发现

### 4.1 行业趋势

1. **AI分类已是标配，但无一例外保留人工兜底。** 金蝶用"AI智能匹配科目"，用友用"AI+专家"HITL模式，Plaid用ML+人工标注。完全自动化的方案不存在。
2. **国内产品更强调"业务单据闭环"。** 金蝶和用友不只是分类，还把流水直接映射到业务单据（凭证、收付款单），这是国内财务SaaS的核心竞争力。
3. **分类策略从"规则驱动"转向"规则+ML混合"。** 早期产品靠用户手工写规则（关键字匹配），现在普遍用ML模型作为默认引擎，规则作为用户自定义覆盖层。
4. **置信度阈值是通用做法。** Plaid和QuickBooks都对低置信度分类标灰或标记待审，不强制自动匹配。

### 4.2 可借鉴的设计

- **三级分类体系：** 业务类型（销售/采购/费用）→ 科目类别 → 具体科目。先粗后细，用户容易理解。
- **用户可覆盖规则：** 默认ML分类，但允许用户对特定流水设置"固定规则"（如"摘要含'物业费' → 管理费用"），规则优先级高于ML。
- **置信度可视化：** 分类结果附带置信度标签（高/中/低），低置信度直接标记待审。

### 4.3 可避免的坑

- **不要承诺100%准确率。** 竞品中没有任何一家做到全自动，Plaid号称10%提升但仍有大量需要人工审核。
- **不要忽略用户自定义规则。** QuickBooks的用户自定义规则是最高频使用的功能之一，没有这个能力用户会感到失控。
- **不要只做分类不做闭环。** 国内竞品普遍在分类后直接生成业务单据，只分类不生成单据的价值减半。

### 4.4 可复用的轮子

- **开源ML分类方案：** 可参考 `bank-ai`（GitHub开源项目，基于BERT的银行交易分类），或使用LLM API做零样本分类（如基于交易描述+金额直接分类）。
- **规则引擎：** 慧财已有规则引擎模块（凭证模板匹配），可复用其匹配逻辑。

## 5. 自身产品切入建议

### 建议一：轻量「规则+LLM」混合方案

**观察基础：** 竞品普遍采用AI+规则+人工的三层架构，但慧财已有银行流水模块和凭证模板匹配引擎。

**方案：**
- **第一层（规则）：** 复用慧财现有凭证模板匹配逻辑（source + businessType + direction + classification），用户可配置"流水摘要匹配规则 → 业务类型"
- **第二层（LLM）：** 对未匹配条目，用LLM基于交易描述+金额+对方户名做零样本分类
- **第三层（人工）：** LLM低置信度条目标记待审，用户确认或修正

**门槛：** 低。规则层已有，LLM调用成本可控，无需训练专用模型。
**风险：** LLM分类结果不可控（幻觉），需严格置信度阈值和人工审核兜底。

### 建议二：深度结合慧财核销架构

**观察基础：** 慧财已有银行流水→B类路由→收款单/付款单→核销工作台的完整链路。

**方案：** 分类结果直接驱动B类路由选择。例如"摘要含'货款'且金额正数"→ B类路由"销售收入"→ 生成收款单 → 进入核销工作台匹配应收。这是竞品（金蝶、用友）都在做的方向，但慧财可以做得更细（核销级而非仅凭证级）。

**门槛：** 中。需要B类路由规则与分类标签的映射配置，以及核销模块的对接。
**风险：** 过度自动化可能违反"所有单据审核必须人工完成"的铁律，需确保分类结果仅为建议，不自动审批。
