# 年度账层评估报告

> **日期**：2026-10-09 | **评估人**：系统评估
> **关联**：DESIGN.md §11 已知局限

## 1. 现状分析

### 1.1 当前期间模型

```
企业 (t_enterprise)
    └── 期间 (t_period: year + month + status)
            └── 凭证 (t_voucher: period_code)
```

- `t_period` 已有 `year` 字段，但**无独立年度实体**
- 期间状态：`open` / `closed` / `locked`（仅月度）
- 结账：`PeriodCloseService` 按月结账

### 1.2 主流竞品模型

| 竞品 | 层级 |
|---|---|
| 用友 U8 | 账套 → 年度 → 会计期间 |
| 金蝶 KIS | 账套 → 年度 → 会计期间 |
| SAP | 公司代码 → 会计年度 → 过账期间 |
| QuickBooks | 公司 → 会计年度 → 期间 |

### 1.3 已具备的年度能力

| 能力 | 状态 | 说明 |
|---|---|---|
| year 字段 | ✅ | `t_period.year` 区分年度 |
| 年度筛选 | ✅ | 报表可按年聚合 |
| 跨年查询 | ✅ | period_code 含年份，可跨期查询 |

### 1.4 缺失的年度能力

| 能力 | 影响 |
|---|---|
| **年结（年度结账）** | 无法锁定全年，12 月后可继续改账 |
| **期初余额结转** | 新年度期初余额需手工录入，无自动从上年期末结转 |
| 年度级配置 | 无年度会计政策/税率独立配置 |
| 年度状态管理 | 无年度 open/closed 状态 |

## 2. 影响评估

### 2.1 对现有业务的影响

| 场景 | 现状 | 风险 |
|---|---|---|
| 跨年记账 | 可通过 period_code 实现 | 无风险 |
| 年度报表 | 按 year 聚合即可 | 无风险 |
| 新年建账 | 需手工录入期初余额 | 中风险，易出错 |
| 年度审计锁定 | 只能按月锁定 12 个月 | 中风险，操作繁琐 |
| 上年数据修改 | 无年度级锁定 | 高风险，可随意改上年账 |

### 2.2 商用化影响

- 中小企业场景：**当前模型基本够用**（按月结账 + 跨年查询可满足）
- 代理记账场景：**有缺口**（多客户年度结转是高频操作）
- 合规审计场景：**有缺口**（年度锁定是审计基本要求）

## 3. 改造方案评估

### 方案 A：引入独立年度实体（t_account_year）

```
企业 → 年度 (t_account_year: status, opening_balance_status)
           └── 期间 (t_period)
```

| 维度 | 评估 |
|---|---|
| 改动范围 | 大（t_period 加 year_id FK，73 张表 period_code 关联需复核） |
| 风险 | 高（period_code 是核心关联字段，改动影响面广） |
| 收益 | 完整年度管理，对齐主流 |
| 工期 | 2-3 周（含数据迁移和回归测试） |

### 方案 B：轻量年结（不新增实体，补年结服务）

```
保持 t_period(year, month) 不变
新增 YearCloseService：
  - 校验 1-12 月全部 closed
  - 锁定全年（将 12 个月 status 设为 locked）
  - 自动生成下年度 1-12 月期间
  - 结转期末余额到下年度期初
```

| 维度 | 评估 |
|---|---|
| 改动范围 | 中（新增 Service + Controller，不改表结构） |
| 风险 | 低（不改动现有关联） |
| 收益 | 解决年结和期初结转核心痛点 |
| 工期 | 3-5 天 |

### 方案 C：维持现状（文档化操作流程）

- 年底手工创建新年度期间
- 手工录入期初余额或通过报表核对
- 通过按月锁定实现年度锁定

| 维度 | 评估 |
|---|---|
| 改动范围 | 无 |
| 风险 | 操作风险 |
| 收益 | 零成本 |
| 适用 | 极小型团队 |

## 4. 建议

**推荐方案 B（轻量年结）**，理由：

1. **解决核心痛点**：年结锁定 + 期初自动结转是商用刚需
2. **风险可控**：不改动 period_code 关联，不影响现有数据
3. **成本适中**：3-5 天可交付，含测试
4. **可演进**：未来如需方案 A，可在 B 基础上平滑升级

### 方案 B 实施清单

| 步骤 | 内容 | 优先级 |
|---|---|---|
| 1 | `YearCloseService.yearClose(year)` — 校验全年已结账 | P0 |
| 2 | 锁定全年期间（status → locked） | P0 |
| 3 | 自动生成下年度 1-12 月期间 | P0 |
| 4 | 期末余额结转到下年度期初（科目余额表期初 = 上年期末） | P0 |
| 5 | `YearCloseController` 端点 + 权限 `period:year-close` | P0 |
| 6 | 前端年结操作入口（期末结账页） | P1 |
| 7 | 反年结（解锁 + 撤销结转，需权限） | P1 |

### 不建议方案 A 的理由

- `period_code`（如 `202606`）是 73+ 张表的关联字段，改动影响面极大
- 中小企业场景下独立年度实体的收益不足以覆盖改造成本
- QuickBooks 同样不做独立年度实体，证明此方案可行

## 5. 结论

当前「企业→期间」模型对**中小企业场景基本够用**，对**代理记账和合规审计场景有缺口**。

建议采用**方案 B（轻量年结）**，以最小改动解决年度结账和期初结转核心问题，无需引入独立年度实体。该方案可作为下一个迭代批次实施。
