# 技术架构

## **1. 项目概述**

### **1.1 产品愿景与定位**

本项目旨在构建一款面向未来的 AI 原生业财协同平台，其核心愿景是通过算力替代人力，彻底重塑传统财务工作流。平台采用 B2B2C 架构设计：一方面，作为面向中小微企业的轻量化管理工具，降低财务管理门槛；另一方面，作为面向代账机构的多账套批量处理引擎，极大提升规模化服务效率。平台的核心价值聚焦于三个维度：合规记账（确保业财数据符合最新财税法规）、实时看账（提供毫秒级财务数据洞察）、智能决策（基于 AI 大模型提供经营分析建议）。

### **1.2 目标用户群体**

平台的核心用户群体分为两类：

1. **中小微企业（老板/财务人员）**：缺乏专业财务团队，需要极简操作、自动合规、随时掌握经营状况的轻量化工具。
2. **代账服务机构（会计/审核人员）**：面临海量账套处理压力，需要批量自动化处理、智能异常拦截、标准化交付的效能引擎。

### **1.3 核心设计理念**

平台的技术演进遵循以下三大设计理念：

1. **传统业财一体化引擎为承重墙，AI Agent 为加速器**：核心账务处理（如凭证、结账、报表）必须依赖确定性、强一致性的传统规则引擎，AI Agent 仅作为辅助提效手段（如票据识别、科目推荐、经营问答），严禁 AI 直接修改核心账务数据。
2. **Human-in-the-loop 人机协同机制**：所有 AI 生成的财务建议或自动化操作，必须经过人工确认（Human Review）方可生效，确保财务合规性与责任可追溯。
3. **SDD+TDD 单人 AI 协同编程范式**：采用 Specification-Driven Development（规范驱动）与 Test-Driven Development（测试驱动）结合的范式。人类负责编写严谨的业务规范（Spec）和不可篡改的单元测试，AI 负责基于 Spec 生成实现代码，通过自动化测试验证，最后由人类进行 Code Review，确保财务核心代码的绝对安全。

## **2. 技术架构设计**

### **2.1 整体架构图**

平台采用“前后端分离 + 微服务 + AI 双引擎”架构，整体分为四层：

1. **接入层（Client Layer）**：包括 PC 管理端、员工移动端、老板看板端，负责多终端交互与数据展示。
2. **网关与路由层（Gateway Layer）**：基于 Spring Cloud Gateway 实现统一鉴权、限流、路由分发，隔离内外网请求。
3. **业务服务层（Service Layer）**：
    - **Java 核心服务**：处理多租户管理、会计科目、凭证引擎、税务核算、期末结转等强一致性业务。
    - **Python AI 服务**：处理票据 OCR、科目推荐、NL2SQL 问答等 AI 密集型任务。
4. **数据与基础设施层（Data & Infra Layer）**：包括 PostgreSQL、Redis、Milvus、MinIO 等存储组件，以及 K8s、ELK 等运维组件。

### **2.2 前端技术栈**

前端采用多端适配策略，以满足不同用户场景：

- **PC 管理端**：Vue3 + Element Plus + TypeScript。选择理由：Vue3 组合式 API 适合复杂表单与表格交互，Element Plus 提供丰富的企业级组件，TypeScript 保障大型项目类型安全。
- **员工移动端**：uni-app 微信小程序。选择理由：一套代码多端发布，微信生态便于消息推送与审批流转。
- **老板看板端**：React Native App / H5 响应式页面。选择理由：RN 提供接近原生的流畅体验，H5 便于通过链接快速分享财务看板。
- **状态管理**：Pinia。选择理由：Vue3 官方推荐，完美支持 TypeScript，比 Vuex 更轻量。
- **HTTP 客户端**：Axios。选择理由：支持请求/响应拦截器，便于统一处理 JWT Token 与全局错误。
- **图表库**：ECharts。选择理由：国内生态完善，支持海量数据渲染与复杂财务图表（如资金流向桑基图）。

### **2.3 后端技术栈**

#### **2.3.1 Java 核心服务层（Spring Boot 3.x）**

Java 层承担财务核心计算，要求极高的稳定性与事务一致性：

- **Web 框架**：Spring Boot 3.2 + Spring MVC。选择理由：最新 LTS 版本，支持虚拟线程（Virtual Threads），大幅提升高并发下的吞吐量。
- **ORM 框架**：MyBatis-Plus 3.5。选择理由：内置强大的多租户插件与分页插件，减少重复 SQL 编写。
- **安全框架**：Spring Security + JWT。选择理由：无状态认证，适合微服务架构，支持细粒度 RBAC 权限控制。
- **缓存与锁**：Redis + Redission 分布式锁。选择理由：Redission 提供看门狗机制，防止凭证号生成等关键操作的死锁。
- **消息队列**：RabbitMQ。选择理由：支持延迟队列与死信队列，适合月末批量结转、异步发票开具等削峰场景。
- **数据库**：PostgreSQL 15。选择理由：原生支持 Schema 级多租户隔离，JSONB 字段支持灵活的辅助核算，强一致性事务支持。
- **规则引擎**：Drools 8.x。选择理由：将复杂的税务规则、凭证转换规则从代码中解耦，支持热更新。

#### **2.3.2 Python AI 服务层（FastAPI）**

Python 层专注 AI 推理与向量检索：

- **Web 框架**：FastAPI。选择理由：基于 ASGI，原生异步支持，自动生成 OpenAPI 文档，性能媲美 Go/Node.js。
- **AI 编排**：LangChain。选择理由：提供标准化的 Agent、Chain、Memory 抽象，便于快速构建 NL2SQL 与 RAG 应用。
- **向量数据库**：Milvus。选择理由：云原生架构，支持十亿级向量检索，适合海量历史凭证的相似度匹配。
- **OCR 引擎**：PaddleOCR / 乐企 API 对接。选择理由：PaddleOCR 开源免费且中文识别率高，乐企 API 提供官方发票验真能力。
- **LLM 集成**：通义千问/文心一言 API。选择理由：国内合规，中文财务语义理解能力强，支持 Function Calling。

### **2.4 数据存储架构**

采用多模态存储策略，按数据特征分类存储：

- **PostgreSQL**：存储核心账务数据（科目、凭证、账簿、报表），满足 ACID 强一致性要求。
- **Redis**：存储会话 Token、分布式锁、热点科目余额缓存，满足毫秒级读取。
- **Milvus**：存储凭证摘要、票据文本的向量索引，支持语义检索。
- **MinIO/OSS**：存储电子发票 PDF、合同影像、银行回单等非结构化文件。

### **2.5 基础设施**

- **容器化**：Docker + Docker Compose（开发/测试），K8s（生产）。
- **服务发现**：Consul / Nacos。选择理由：支持配置中心与服务注册发现双功能。
- **API 网关**：Spring Cloud Gateway。选择理由：与 Spring 生态无缝集成，支持动态路由。
- **日志监控**：ELK Stack + Prometheus + Grafana。
- **CI/CD**：Jenkins/GitLab CI，实现自动化测试与灰度发布。
