## 二、高危问题清单（17 项 — 必须在 Agency 开发启动前修复）

### H-01：多租户术语冲突（tenant_id vs enterprise_id）

- **严重度**：🔴 高危 — 阻塞 Agency 开发
- **位置**：S-01 全文用 `tenant_id`/`t_tenant`/`TenantEntity`/`TenantContextHolder`；S-26 和多租户架构设计用 `enterprise_id`/`t_enterprise`/`EnterpriseEntity`/`EnterpriseContextHolder`
- **影响**：S-26 声明"S-26 是 S-01 的实现落地"，但两份 Spec 在最核心的隔离字段命名上完全分叉，开发者无从选择权威源
- **修复方案**：统一为 `enterprise_id` 方案（与架构设计文档和实际代码走向一致），S-01 顶部加声明"已被 S-26 取代，tenant_id 概念等价于 enterprise_id"

### H-02：SPEC 编号体系双轨制

- **位置**：Spec 文档自报 `HUICAI-SPC-100/101/126`；REQUIREMENTS_REGISTRY 使用 `SPC-001/004/126-S-26` 等不同编号

### H-16：P40-input BDD 与 AT 严重不对应

## 九、规划-开发-测试闭环评估

### 9.1 闭环执行情况

| 环节 | 规范要求 | 实际执行 | 评分 |
|------|---------|---------|------|
| SPEC 先于代码 | 每个功能先写 SPEC | 98% SPEC 遵循 SDD 四段模板 | ✅ 优秀 |
| 审核门 | 老丁审核后才执行 | S-26 标"⚠️ 待老丁审核" | ✅ 合规 |
| TDD Red→Green | 先写测试再写实现 | 部分执行，有假阳性 | ⚠️ 需改进 |
| 负向断言强制 | 状态机必须验证"不该做的没做" | 4/8 个状态机未做 | ❌ 不合规 |
| 测试 0 fail | mvn test Failures=0 | 当前 2 个失败 | ❌ 不合规 |
| 全量回归 | 每个 Sprint 结束 mvn test | 测试矩阵数字落后 | ⚠️ 需更新 |
| 文档同步 | 代码变更后同步文档 | 多处文档漂移 | ❌ 需修复 |

### 9.2 闭环缺口

1. **TDD 执行不彻底**：存在伪测试（`expect(true).toBe(true)`）和虚报测试（矩阵声称 31 个实际 0 个），TDD 流程被架空
2. **负向断言缺失**：4 个状态机测试仅验证前置条件，不验证副作用，违反铁律
3. **并发测试失效**：1 个 @Disabled + 1 个无断言，核心写操作零并发覆盖
4. **CI 集成缺失**：check-entity-schema.mjs 和 validate_spec_contract.py 未集成 CI
5. **文档与代码漂移**：测试矩阵、需求登记册、文档注册表数字均落后于代码实际状态

## 十、结论与建议

### 10.1 总体评价

慧财财务系统在 **SPEC Coding 框架遵循度** 上表现优秀（98% SDD 模板、91% BDD 覆盖率），文档体系完整（200+ 文档），架构设计合理（三层防线、base/sme/agency 分层）。但存在 **17 个高危问题**，集中在：

1. **多租户术语冲突**（tenant_id vs enterprise_id）— 阻塞 Agency 开发
2. **SPEC 编号双轨制** — 需求追溯链断裂
3. **测试可信度问题** — 虚报测试 + 伪测试 + 无断言并发测试
4. **文档注册表失同步** — 新文档未登记、编号冲突、死链

### 10.2 建议执行顺序

```
第一步：修复 17 个高危问题（P0）
  ├── 文档修复（H-01~H-08）：统一术语 + 统一编号 + 补登记 + 修死链
  └── 测试修复（H-09~H-17）：重写伪测试 + 补状态机测试 + 修并发测试

第二步：启动 Agency Sprint 1 开发
  └── 前置条件：P0 全部修复 + mvn test Failures=0

第三步：修复 14 个中危问题（P1）
  └── 迭代中逐步修复

第四步：同步文档数字
  └── 测试矩阵 + 需求登记册 + 文档注册表 全量更新
```

### 10.3 长期治理建议

1. **将 check-entity-schema.mjs 集成 pre-commit hook**：每次 Entity 变更自动检查 DB 一致性
2. **将 validate_spec_contract.py 集成 CI**：SPEC 变更时自动校验 BDD:AT 1:1 对应
3. **建立测试可信度审计机制**：定期检查测试矩阵与实际代码的一致性
4. **统一文档元数据模板**：在 SPEC-CONTRACT-SCHEMA 中定义强制头部格式
5. **建立文档注册表自动校验脚本**：检测未登记文档和编号冲突
