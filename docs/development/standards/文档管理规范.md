## 一、文档编号体系

所有项目文档必须分配唯一编号，格式 `HUICAI-{分类}-{NNN}`：

| 分类 | 前缀 | 范围 | 说明 |
|------|------|------|------|
| 主文档 | MAIN | 001 | DESIGN.md |
| 设计文档 | DES | 001~999 | design/ 目录 |
| 架构文档 | ARC | 001~999 | architecture/ 目录 |
| 规格文档 | SPC | P0~P99 | specs/ 目录（沿用 P 编号） |
| 开发文档 | DEV | 001~999 | development/ 目录 |
| 测试文档 | TST | 001~999 | testing/ 目录 |
| 参考文档 | REF | 001~999 | reference/ 目录 |

**编号分配规则：**
- 新增文档前先查 [DOCUMENT_REGISTRY.md](../../DOCUMENT_REGISTRY.md) 获取下一个可用序号
- 编号一旦分配不可复用（即使文档已废弃）
- 废弃文档在注册表中标记「已归档」

## 二、文档头部格式

每份文档必须在开头包含标准化头部：

```markdown
> **编号**：HUICAI-{CAT}-{NNN}
> **版本**：V{x}.{y}
> **修改日期**：YYYY-MM-DD
> **修改人**：{name}
> **修改内容**：{简要描述本次修改的主要内容}
```

### 头部字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| 编号 | 是 | 唯一文档编号 |
| 版本 | 是 | 语义版本号，首次 V1.0 |
| 修改日期 | 是 | ISO 格式 YYYY-MM-DD |
| 修改人 | 是 | 实际操作人 |
| 修改内容 | 是 | 一句简要描述变更原因 |

### 版本号规则

| 变更类型 | 版本号变化 | 示例 |
|---------|-----------|------|
| 初始创建 | V1.0 | — |
| 微小修正（错别字/格式） | 小数点递增 | V1.0 → V1.1 |
| 内容增删（新增章节/修改内容） | 次版本号递增 | V1.0 → V2.0 |
| 架构/设计重大变更 | 大版本号递增 | V2.0 → V3.0 |

## 三、文档生命周期

### 3.1 新增流程

```
① 确认编号 → 查 DOCUMENT_REGISTRY.md 获取下一个序号
② 写内容 → 按标准头部格式
③ 登记 → 在 DOCUMENT_REGISTRY.md 追加一行
④ 提交 → git commit + push
```

### 3.2 修改流程

```
① 修改文档内容
② 更新头部：版本号 + 修改日期 + 修改人 + 修改内容
③ 更新注册表对应行的版本/日期/修改人
④ 提交 → git commit + push
```

### 3.3 废弃流程

```
① 将文档移入 archive/ 目录
② 在 DOCUMENT_REGISTRY.md 对应行标记「已归档」
③ 保留编号，不可复用
```

## 四、文档目录规范

```
docs/
├── DESIGN.md                     ← 主设计文档（仅全局共识和索引）
├── DOCUMENT_REGISTRY.md          ← 文档注册表（权威索引）
├── design/                       ← 模块设计文档
├── architecture/                 ← 架构文档
├── specs/                        ← 规格文档（P系列）
├── development/                  ← 开发文档
│   ├── plans/                    ← 开发计划
│   ├── tasks/                    ← 任务书
│   ├── workflows/                ← 工作流
│   ├── requirements/             ← 需求分析
│   ├── standards/                ← 开发规范
│   ├── guides/                   ← 操作指南
│   └── lessons/                  ← 经验教训
├── testing/                      ← 测试文档
│   ├── plans/                    ← 测试计划
│   └── standards/                ← 测试标准
├── reference/                    ← 参考文档
└── archive/                      ← 已归档文档
```

### 文件命名规则

- 使用有意义的文件名，中文优先
- 多文档系列使用 `{序号}-{名称}` 前缀（如 `00-system-design.md`）
- 避免文件名过长（建议不超过 60 字符）

## 五、开发工作流中的文档义务

### 每次开发任务必须包含的文档操作

| 阶段 | 必须操作 |
|------|---------|
| **SPEC 阶段** | 确认文档编号 + 更新 DESIGN.md 模块索引（如有模块变更） |
| **开发完成** | 更新对应设计文档的版本号 + 修改内容 |
| **提交前** | 检查 DOCUMENT_REGISTRY.md 是否已同步 |

### 不需要修改文档的场景

- 纯 Bug 修复（不改设计/API/数据模型）
- 重构内部实现（不改接口/行为）
- 测试追加（不改变模块设计）

---

## 六、违反规范的后果

| 违规范畴 | 后果 |
|---------|------|
| 新增文档未编号 | 开发任务不通过审核 |
| 修改文档未更新头部 | 下次文档审计时标记 |
| 注册表未同步 | 开发任务不通过审核 |
| 文档移入错误目录 | 代码审查时要求修正 |
