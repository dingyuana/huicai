# 慧财财务 — 发票与凭证状态机需求分析书

> 版本：V1.0 | 日期：2026-06-21 | 归属：Phase 2（业务单据核心）
>
> 本文件描述慧财财务系统中"发票"与"凭证"两类核心单据的状态机定义、三类发票（销售/采购/费用）的完整业务流程，以及强制校验与不可修改铁律。与 SPEC `docs/specs/P20-arap-state-machine-spec.md`（应收应付状态机）、`P18-declaration-state-machine.md`（申报状态机）互为补充——本文件定"全场景状态契约与流程骨架"，SPEC 定"特定模块状态实现"。

## 📌 文档定位

本需求分析书是 `基于Web财务软件的项目说明书.md` 第 §4.4 节（发票管理）、§4.6 节（凭证管理）、§4.8 节（核销管理）的综合展开，回答"状态如何流转、触发条件是什么、哪些不可逆"的问题。

**适用范围**：人民币单一币种、纯财务核算场景。不含外币折算、不含集团合并报表。

## 一、核心设计理念

| 理念 | 说明 |
|:---|:---|
| **状态机先行** | 所有业务流转基于状态字段判断，禁止使用"金额是否为空""日期是否晚于"等模糊条件 |
| **价税分离强制** | 进项/销项税额必须独立科目核算，普票税额直接并入费用 |
| **不可修改铁律** | 已过账凭证禁 UPDATE/DELETE，只能通过红字冲销记录对冲 |
| **强制校验时机** | 保存校验借贷平衡；过账校验现金流分配 + 辅助核算挂载 |
| **全操作可追溯** | 状态每一次变更必须走 `audit_log` 表，记录变更人、原值、新值、原由 |

## 二、用户角色与职责

| 角色 | 职责 |
|:---|:---|
| **发票录入员** | 导入发票（OCR / 税局接口 / Excel）；处理"待确认"发票 |
| **应收/应付会计** | 审核发票；选择结算状态生成凭证；发起/确认核销 |
| **总账会计** | 审核凭证；过账；处理账期错位 |

| **财务主管** | 审批大额/特殊凭证；驳回或批准状态例外流转；查看审计日志 |
| **系统管理员** | 配置商品-科目映射、客商-往来科目映射、现金流项目映射 |

## 三、核心单据状态定义

### 3.1 发票状态机

| 状态 | 含义 | 终态？ |
|:---|:---|:---:|
| `PENDING_CONFIRM` 待确认 | 导入后未匹配客户/科目或缺关键字段 | 否 |
| `PENDING_REVIEW` 待审核 | 信息完整，等待财务主管确认 | 否 |
| `CONFIRMED` 已确认 | 审核通过，等待生成凭证 | 否 |
| `VOUCHER_GENERATED` 已生成凭证 | 已生成凭证，记录 `voucher_id` | 否 |
| `FULLY_RECONCILED` 已核销 | 挂账金额=0 | **是** |
| `PARTIALLY_RECONCILED` 部分核销 | 挂账金额>0 但已发生核销 | 否 |
| `VOIDED` 已作废 | 发现错误，整张作废 | **是** |

**状态流转规则**：

```
PENDING_CONFIRM ──匹配成功──→ PENDING_REVIEW ──审核通过──→ CONFIRMED
        │                              │                          │
        │                              ↓                          ↓
        │                         (审核驳回)                 生成凭证触发
        │                              │                          │
        │                              └──────────┬───────────────┘
        │                                         ↓
        │                              VOUCHER_GENERATED
        │                                         │
        │                                         ↓
        │                              ┌────核销────┐
        │                              ↓           ↓
        │                    FULLY_RECONCILED  PARTIALLY_RECONCILED
        │
        └─────────任意非终态────→ VOIDED（需权限 + 记录原由）
```

**允许的回退**（业务必需）：
- `CONFIRMED → PENDING_REVIEW`：选错结算状态时可回退（财务主管权限）
- `VOUCHER_GENERATED → CONFIRMED`：凭证尚未提交审核时可回退（**仅限凭证状态=草稿**）

**禁止的回退**：
- 已过账的发票不能回退到任何前置状态
- 已核销发票必须通过"反向核销单"才能变更（不影响已过账凭证）

### 3.2 凭证状态机

| 状态 | 含义 | 终态？ |
|:---|:---|:---:|
| `DRAFT` 草稿 | 手工录入或自动生成未提交 | 否 |
| `PENDING_REVIEW` 待审核 | 提交后等待审核人处理 | 否 |
| `APPROVED` 已审核 | 审核通过，可记账 | 否 |
| `POSTED` 已过账 | 已登记总账，科目余额已更新 | **是** |
| `REVERSED` 已冲销 | 被红字凭证完全冲销 | **是** |
| `REJECTED` 作废 | 审核不通过或被驳回 | **是** |

**状态流转规则**：

```
DRAFT ──提交──→ PENDING_REVIEW ──审核通过──→ APPROVED ──过账──→ POSTED
  │                    │                          │               │
  │                    ↓                          ↓               │
  │              (审核驳回)                    (反过账)            │
  │                    │                          │               │
  │                    └─────→ REJECTED           └──────→ DRAFT   │
  │                                                                      │
  └──────────────────────────────────────────────────────────────────────┘
                              (强制流程：禁止绕过审核/过账直接删除)

                          POSTED ──生成红字凭证──→ REVERSED
                              (双方都变为 REVERSED，原凭证保留只读)
```

**绝对禁止的操作**：
- `POSTED` 状态的凭证：`UPDATE` 任意字段、`DELETE` 记录——**数据库层面硬约束**
- `POSTED` 凭证唯一修正路径：INSERT 一条 `reverse_voucher_id` 指向原凭证的红字凭证
- 红字凭证借贷方向与原凭证相反，金额绝对值相等，自动绑定 `reversal_pair_id`

## 四、三种发票的完整流程

### 4.1 销售发票（我方开票）

**流程总览**：发票导入 → 确认收入（生成凭证）→ 收款核销

#### FR-S-1：发票导入与确认

| 属性 | 要求 |
|:---|:---|
| 导入方式 | OCR 识别、电子税局接口、Excel 导入 |
| 必填字段 | 发票代码、号码、日期、客户名称、商品明细、不含税金额、税额、价税合计 |
| 自动匹配 | 客户名称 → 客户档案；商品/服务 → 科目映射表 |
| 失败处理 | 任意匹配失败 → 状态 `PENDING_CONFIRM`，提示人工选择或新建 |

**系统动作**：
1. 校验 `发票代码+号码` 全局唯一性（联合索引）
2. 客户名称模糊匹配 `customer` 表，匹配失败置 `PENDING_CONFIRM`
3. 根据商品-科目映射填充借方"主营业务收入"+ "应交税费-应交增值税(销项税额)"
4. 新商品无映射时置 `PENDING_CONFIRM`
5. 状态流转：`PENDING_CONFIRM → PENDING_REVIEW`

#### FR-S-2：生成凭证（价税分离与债权确认）

**触发点**：发票状态 = `CONFIRMED`，财务人员点击"生成凭证"。

**强制弹窗**：必须选择结算状态（`A`/`B`/`C` 三选一）。

| 选项 | 借方 | 贷方 | 凭证字 | 附加动作 |
|:---|:---|:---|:---:|:---|
| **A 未收款（赊销）** | 应收账款—[客户ID] | 主营业务收入 + 应交税费-销项税 | 转 | 挂客户辅助核算 |
| **B 已收款（现结）** | 银行存款—[银行账户ID] | 主营业务收入 + 应交税费-销项税 | 收 | **强制**弹出"现金流量分配"，关联"销售商品、提供劳务收到的现金" |
| **C 冲销预收** | 预收账款—[客户ID] | 主营业务收入 + 应交税费-销项税 | 转 | 查询客户预收余额，不足时**警告但允许保存**（可配置严格阻断） |

**状态流转**：发票 → `VOUCHER_GENERATED`，记录 `voucher_id`；凭证 → `DRAFT`。

#### FR-S-3：收款与核销（仅选项A）

**触发点**：出纳收到银行回单，录入"收款单"。

**收款单字段**：收款银行账户、金额、付款方（客户）、收款日期。

**收款单自动生成凭证**：
```
借：银行存款—[银行账户ID]
    贷：应收账款—[客户ID]  (待核销状态)
附加动作：分配现金流量项目
凭证字：收
```

**核销动作**（`docs/specs/P20-arap-state-machine-spec.md` 已定义，此处引用）：

| 步骤 | 系统行为 |
|:---|:---|
| 1. 加载候选 | 系统加载该客户所有 `PARTIALLY_RECONCILED` / `PENDING_RECONCILIATION` 发票 |
| 2. 匹配规则 | **默认 FIFO**；**支持人工指定**（精细化预收账款管理必需） |
| 3. 尾差处理 | 若存在尾差，强制弹窗将差额记入"财务费用"，**正负方向由系统自动识别，绝对值入账** |
| 4. 数据记录 | `reconciliation_relation` 表记录 `receipt_id` / `invoice_id` / `reconciled_amount` |
| 5. 状态更新 | 发票 → `FULLY_RECONCILED` 或 `PARTIALLY_RECONCILED`；冗余字段 `unsettled_amount` 实时更新 |

### 4.2 采购发票（我方收票）

**流程总览**：发票导入 → 确认成本/资产（生成凭证）→ 付款核销

#### FR-P-1：发票导入与确认

| 属性 | 要求 |
|:---|:---|
| 自动匹配 | 供应商名称 → 供应商档案；物料/服务 → 借方科目（原材料/库存商品/主营业务成本）+ 进项税科目 |
| 专票/普票判定 | 根据发票类型字段，进项税可抵扣性自动处理 |
| 状态流转 | `PENDING_CONFIRM → CONFIRMED`（采购发票可不经过 `PENDING_REVIEW`，由供应商匹配度决定） |

#### FR-P-2：生成凭证

| 选项 | 借方 | 贷方 | 凭证字 |
|:---|:---|:---|:---:|
| **A 未付款（赊购）** | 成本/费用/资产科目 + 应交税费-进项税 | 应付账款—[供应商ID] | 转 |
| **B 已付款（现付）** | 成本/费用/资产科目 + 应交税费-进项税 | 银行存款—[银行账户ID] | 付 |
| **C 核销预付** | 成本/费用/资产科目 + 应交税费-进项税 | 预付账款—[供应商ID] | 转 |

**选项B附加动作**：**强制**分配现金流"购买商品、接受劳务支付的现金"。

**状态流转**：发票 → `VOUCHER_GENERATED`。

#### FR-P-3：付款与核销

**付款单凭证**：
```
借：应付账款—[供应商ID]
    贷：银行存款—[银行账户ID]
附加动作：分配现金流量项目
```

**核销逻辑**：与销售发票对称，付款单与采购发票的"应付账款"对冲。

**现金折扣处理**：
- 折扣金额自动识别（付款金额 < 应付金额）
- 折扣部分生成独立凭证：
  ```
  借：应付账款—[供应商ID]
      贷：财务费用—现金折扣  (红字，或借方红字)
  ```
- 折扣不可直接冲减发票金额，必须保留发票完整金额 + 独立折扣凭证

### 4.3 费用发票（差旅/招待/房租等）

**流程总览**：发票导入 → 确认费用（生成凭证）→ 报销付款

#### FR-E-1：发票导入与确认（去重是刚需）

**强制去重校验**：
```
SELECT COUNT(*) FROM invoice
WHERE invoice_code = ? AND invoice_number = ?
  AND status IN ('CONFIRMED', 'VOUCHER_GENERATED', 'FULLY_RECONCILED', 'PARTIALLY_RECONCILED')
HAVING COUNT(*) > 0
```
- 一旦命中，立即阻断并提示"疑似重复报销"
- `invoice_code + invoice_number + invoice_source` 联合唯一索引（不同税局号码可能撞）

**用途匹配**：让用户选择费用类型（管理费用-差旅费/销售费用-业务招待费/管理费用-房租等），自动填充借方科目。

**价税分离**：
| 发票类型 | 进项税处理 |
|:---|:---|
| 增值税专用发票 | 独立科目"应交税费-应交增值税(进项税额)"，可抵扣 |
| 增值税普通发票 | 税额直接并入费用科目，**不进项税** |
| 电子发票 | 同专票/普票规则，根据发票类型字段判定 |

#### FR-E-2：生成凭证（通常与付款同步）

| 场景 | 借方 | 贷方 | 凭证字 | 辅助核算 |
|:---|:---|:---|:---:|:---|
| **员工垫付，公司报销** | 费用科目 + 进项税(专票) | 银行存款 | 付 | **强制**挂个人/员工辅助核算 |
| **对公挂账未付** | 费用科目 + 进项税(专票) | 应付账款-供应商 | 转 | 挂供应商辅助核算 |

**状态流转**：发票 → `VOUCHER_GENERATED`。

## 五、强制校验规则

### 5.1 保存校验

| 校验项 | 规则 | 失败处理 |
|:---|:---|:---|
| 借贷平衡 | 借方合计 = 贷方合计（精度 0.01） | 阻断保存 |
| 必填字段 | 凭证日期、凭证字、摘要、借/贷科目、金额 | 阻断保存 |
| 科目有效性 | 所有科目必须存在于 `chart_of_accounts` 且未停用 | 阻断保存 |
| 客商辅助核算 | 涉及应收/应付/预收/预付的科目必须挂客商 | 阻断保存 |

### 5.2 过账校验

| 校验项 | 规则 | 失败处理 |
|:---|:---|:---|
| 现金流量分配 | 涉及现金/银行/其他货币资金的科目必须已分配现金流量项目 | 阻断过账 |
| 账期一致性 | 凭证 `accounting_period` (YYYY-MM) 必须在当前账期或已结账账期 | 阻断过账 |
| 跨期标记 | 发票日期与凭证 `accounting_period` 不一致时强制标记 `cross_period=true` | 警告但允许 |
| 审核人 ≠ 制单人 | `voucher.created_by ≠ voucher.reviewed_by` | 阻断过账 |
| 大额阈值 | 金额 > 阈值（如 10 万）需财务主管二级审批 | 阻断过账 |

### 5.3 账期控制

**新增字段**：`voucher.accounting_period VARCHAR(7)`（格式 `YYYY-MM`）。

**过账逻辑**：
```
IF voucher.accounting_period = current_period:
    直接过账
ELIF voucher.accounting_period < current_period AND period.status = 'CLOSED':
    拒绝过账（已结账账期不可补录）
ELIF voucher.accounting_period < current_period AND period.status = 'OPEN':
    允许过账 + 标记 cross_period=true
ELSE (future period):
    拒绝过账（未来账期不允许）
```

**资产负债表口径**：报表生成时严格按 `accounting_period` 字段汇总，不按 `posting_date`——避免跨期错位。

## 六、审计追踪

**所有状态变更必须走 `audit_log` 表**，不允许直接 `UPDATE status` 绕过。

```sql
CREATE TABLE audit_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    entity_type VARCHAR(50) NOT NULL,           -- 'invoice' / 'voucher'
    entity_id BIGINT NOT NULL,
    field_name VARCHAR(50) NOT NULL,            -- 'status' / 'amount' / ...
    old_value TEXT,
    new_value TEXT,
    change_reason VARCHAR(500),
    changed_by BIGINT NOT NULL,                 -- user_id
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_entity (entity_type, entity_id),
    INDEX idx_changed_at (changed_at)
);
```

**触发审计的状态变更**：
- 所有 `invoice.status` 字段变更
- 所有 `voucher.status` 字段变更
- `voucher.amount` 变更（仅限 `DRAFT`/`REJECTED` 状态）
- 红冲操作（记录 `original_voucher_id` + `reversal_reason`）

**API 层硬约束**：
- `InvoiceService.updateStatus()` 必须先 INSERT `audit_log` 再 UPDATE 业务表（同事务）
- 异常情况下回滚，保证审计与业务一致性

## 七、并发与幂等性

### 7.1 行级锁

**所有状态变更操作必须使用行级锁**：
```java
@Transactional
public void updateInvoiceStatus(Long id, InvoiceStatus newStatus) {
    Invoice inv = invoiceMapper.selectByIdForUpdate(id);  // SELECT ... FOR UPDATE
    if (!canTransition(inv.getStatus(), newStatus)) {
        throw new IllegalStateException(...);
    }
    invoiceMapper.updateStatus(id, newStatus);
    auditLogService.record(...);
}
```

### 7.2 乐观锁

**关键业务表加 `version` 字段**：
```sql
ALTER TABLE invoice ADD COLUMN version INT NOT NULL DEFAULT 0;
ALTER TABLE voucher ADD COLUMN version INT NOT NULL DEFAULT 0;
```

**MyBatis Plus 配置**：`@Version` 注解，UPDATE 时自动带 `WHERE version=?`，更新失败抛 `OptimisticLockException`。

### 7.3 幂等性

**重复提交防护**：
- 发票导入：`invoice_code + invoice_number + invoice_source` 联合唯一约束
- 凭证生成：`invoice_id` 唯一约束（一发票只能生成一凭证，已 `VOUCHER_GENERATED` 的发票重复触发返回原 `voucher_id`）
- 核销：`reconciliation_relation (receipt_id, invoice_id)` 联合唯一约束

## 八、数据精度与编码规范

### 8.1 金额精度

| 字段类型 | Java 类型 | 小数位 | 舍入规则 |
|:---|:---|:---:|:---|
| 发票金额 | `BigDecimal` | 4 位（增值税单价精度）| `HALF_UP` |
| 凭证金额 | `BigDecimal` | 2 位 | `HALF_UP` |
| 核销金额 | `BigDecimal` | 2 位 | `HALF_UP` |
| 汇率 | `BigDecimal` | 6 位 | `HALF_UP`（预留扩展，本期不实现）|

### 8.2 编码规范

**数据库层**：
- 所有金额字段 `DECIMAL(20, 4)`（发票）/ `DECIMAL(20, 2)`（凭证）
- 所有 ID 字段 `BIGINT`，不使用 UUID（性能 + 索引空间）
- 所有时间字段 `TIMESTAMP`，统一 UTC 存储 + 业务层按 Asia/Shanghai 展示

**应用层**：
- 禁止使用 `double` / `float` 处理金额
- 所有金额运算必须通过 `BigDecimalUtil`（项目统一工具类）
- 数据库比较使用 `compareTo`，禁止 `equals`（精度差异）

## 九、客商主数据合并场景（V1.1 预告）

**业务场景**：客户 A 改名后想并入客户 B（统一税务抬头、合并报表）。

**当前限制**：历史发票挂账仍在 A 名下，导致：
- 应收账款余额分散
- 客户对账单无法合并
- 报表客户维度不准确

**V1.1 解决思路**（本期不实现）：
- 增加 `customer_merge_log` 表，记录合并操作
- 合并操作生成"客户转移凭证"：
  ```
  借：应收账款—B
      贷：应收账款—A
  ```
- 历史发票 `customer_id` 不变，查询时通过 `customer_merge_log` 关联到当前有效客户

**本期规避策略**：
- 客户录入时强制校验名称唯一性（提示"已存在相似名称客户，是否新建"）
- 财务主管可手动调整 `invoice.customer_id`（仅限 `PENDING_CONFIRM` / `PENDING_REVIEW` 状态）

## 十、非功能需求

### NFR-1：性能

| 指标 | 要求 |
|:---|:---|
| 发票批量导入 | 500 张/批，≤ 10 秒完成解析 + 匹配 |
| 凭证生成响应 | ≤ 2 秒（含价税分离 + 现金流分配弹窗准备） |
| 核销匹配查询 | 单客户未核销发票加载 ≤ 1 秒（千张量级）|
| 状态机查询 | 单据详情加载 ≤ 500ms（含状态流转历史）|

### NFR-2：安全

- 状态流转必须记录 `changed_by`，事后可追溯到人
- `VOIDED` / `REVERSED` / `REJECTED` 操作需要二次确认 + 原由录入
- 金额 > 100,000 元的状态变更触发敏感操作日志（独立表）

### NFR-3：可观测性

- 所有状态变更事件发布到 Kafka topic `invoice.status.changed` / `voucher.status.changed`
- 审计日志保留期：永久（财务合规要求）
- 关键指标埋点：`state_transition_total{from, to, entity_type}` / `cross_period_voucher_total`
