## 0. 背景与现状

P85 覆盖 PRD-017 三个子项。代码 trace 后**三项的实际规模都与 PRD 预判有出入**，逐项说明。

### P85-A：`generateProfitCarryOver` 全表扫描 + N+1

原实现用 `voucherEntryMapper.selectList(null)` 取**全部**凭证分录（跨所有期间、所有租户），Java 侧再逐条 `selectById` 查凭证头拿 period 过滤，且对每个分录调 `subjectService.getById` 查科目。三个问题叠加：

1. `selectList(null)` 全表读，数据量增长后不可接受（PRD P85-BD2 要求 10 万行 <2s）
2. 对每条分录 `selectById` → N+1 查询
3. 对每个分录 `subjectService.getById` → 又一层 N+1

### P85-B：`t_close_log` 完全不存在

`listCloseLog()` 原为**空实现**（`return new ArrayList<>()`）。没有 migration、没有 Entity、没有 Mapper——结账日志是 PRD-017 明确要求的审计能力，但此前完全未落地。

### P85-C：折旧结转缺失

P77 已交付折旧**计提**（`AssetCardService.depreciatePeriod` 写入 `t_asset_depreciation`），但**计提 ≠ 制证**——计提结果从未被转成凭证。`t_asset_depreciation.voucher_id` 字段存在但从未被填充，折旧费用只留在资产台账里，不进总账，不进利润表。

## 1. 改动契约

### 1.1 P85-A 副作用声明

| 方法 | 改动 | 事务 |
|---|---|---|
| `PeriodCloseServiceImpl.generateProfitCarryOver(period, userId)` | 内部实现替换：`selectList(null)` + N+1 → 单条聚合 SQL `selectProfitSubjectTotals(period)`。**签名不变**（S-17 契约不回退），调用方无感 | `@Transactional`（既有） |
| `VoucherEntryMapper.selectProfitSubjectTotals(period)` | 新增方法 + XML 聚合 SQL | 纯读 |

**聚合 SQL 设计要点：**

```sql
SELECT s.id AS subject_id, s.code, s.name, s.direction,
       SUM(e.debit_amount) AS debit_total, SUM(e.credit_amount) AS credit_total
FROM t_voucher_entry e
JOIN t_voucher v ON e.voucher_id = v.id
JOIN t_subject s ON e.subject_id = s.id
WHERE e.deleted = 0 AND v.deleted = 0 AND v.status = 'POSTED'
  AND v.period = #{period} AND s.deleted = 0 AND s.code LIKE '6%'
GROUP BY s.id, s.code, s.name, s.direction
HAVING ABS(SUM(e.debit_amount) - SUM(e.credit_amount)) <> 0
```

- `JOIN t_voucher` 过滤 `status='POSTED'` + `period=#{period}`——只算已过账的本期凭证
- `code LIKE '6%'` 直接筛损益类科目，不再查全表
- `HAVING ABS(debit-credit) <> 0` **只取净额非零的科目**

**HAVING 条件选型（实测踩坑）：** 初版用 `HAVING debit <> 0 OR credit <> 0`，测试发现**借贷对冲的科目（借=贷，净额为 0）也被捞出来**——例如管理费用 100 / 累计折旧 100 这种同金额双向科目。这类科目结转后对损益零贡献，却生成一对抵消分录，纯粹噪音。改为 `ABS(debit - credit) <> 0` 后正确排除。

### 1.2 P85-B 副作用声明

| 对象 | 内容 |
|---|---|
| `V151__create_close_log.sql` | 新增 `t_close_log` 表（period / action / operator_id / result / detail / duration_ms + BaseEntity 字段），含 `chk_close_log_result` CHECK 约束 |
| `CloseLogEntity` + `CloseLogMapper` | Entity 自定义 `operator_id` 列，**不复用** `created_by` |
| `PeriodCloseServiceImpl.appendCloseLog(...)` | 新增私有方法，try-catch 包裹（日志失败不阻断结账主流程） |
| `closePeriod` / `reopenPeriod` | 接入 `appendCloseLog`，记录动作 + 操作者 + 耗时 |
| `listCloseLog(period)` | 空实现 → 查 `t_close_log` 按时间倒序 |

**`operator_id` 为什么单独建列：** `BaseEntity.createdBy` 标了 `@TableField(exist=false)`，MyBatis-Plus 根本不生成该列的 INSERT。想追溯操作者必须建自定义列，不能指望复用 `created_by`。

**建表用 `GENERATED BY DEFAULT AS IDENTITY`：** 项目的 `SchemaValidator` 在启动时校验全部企业级表 id 列必须 `is_identity=YES`，否则抛 `IllegalStateException` 直接启动失败。`BIGSERIAL` 的 `is_identity=NO` 不通过。用 `BY DEFAULT`（非 `BY ALWAYS`）是为了允许测试 helper 显式插入 id。

### 1.3 P85-C 副作用声明

| 对象 | 内容 |
|---|---|
| `DepreciationVoucherService` + `Impl`（sme.asset） | 新增：按期间读已计提折旧 → 生成 DEPR DRAFT 凭证 |
| `DepreciationVoucherResult`（DTO） | 返回 voucherId / voucherNo / totalDebit / totalCredit / detailCount / status |
| `AssetCardController` | 新增 `POST /depreciation-voucher/{period}` 端点 |
| `V152__seed_subject_1602_*.sql` | 补 seed 1602 累计折旧科目（见 §2 数据缺口） |
| `t_asset_depreciation.voucher_id` | 制证后回写溯源（仅当为 NULL 时写，已回填的跳过） |

**分录口径：**

```
借 6602 管理费用    <合计本期折旧>
贷 1602 累计折旧    <合计本期折旧>
```

金额来源是 `t_asset_depreciation.depreciation_amount` 按 period 汇总——**制证绝不自行计算折旧**，只读计提结果。

**架构约束（实测确认）：** 实现放在 `com.huicai.sme.asset` 而非 `base.voucher`。实测 `base.voucher` 对 `sme.*` **零反向依赖**，项目内依赖方向严格单向 `sme → base`（sme/cash、sme/arap、sme/tax 均已如此）。因此 **P84 的 `generate-sequence` 编排只能在 Controller 层完成**，不能在 `base.voucher` 的 Service 里调资产模块。

**幂等键 `DEPR-{period}`：** 凭证号由本方法统一赋值（不走 `voucherNoService.generateNextNo`），既是幂等键又是反结账扫描前缀。P87 的 `reopenPeriod` 已按 `CLOSE-`/`DISTRIB-`/`DEPR-` 三个前缀扫描 DRAFT 凭证，本凭证号必须落在这个约定内，否则反结账会漏扫。

**为什么直接 `voucherMapper.insert` 而非 `VoucherService.create()`：** `create()` 会用 `voucherNoService` 生成递增凭证号，无法固定为 `DEPR-{period}`。sme/tax（`TaxServiceImpl`）、sme/arap（`BadDebtServiceImpl`）都是直接 insert 的模式。

**期间校验用 `PeriodService.getByPeriodCode()`** 而非 `lambdaQuery()`——后者在 Mockito 里需 mock `LambdaQueryChainWrapper`，且 `getByPeriodCode` 是既有语义等价方法。

## 2. 附带发现：1602 累计折旧科目缺失（真实数据缺口）

`V102_5__seed_template_lines_and_base_subjects.sql` seed 了 16 个基础科目，**有 `1601 固定资产` 但漏了 `1602 累计折旧`**。dev 库里 1602 存在是人工补建的——Testcontainers 从零跑 Flyway 时该科目不存在，折旧制证直接报"未配置科目 1602"，功能完全不可用。

已写 `V152` 补 seed。两个坑：

1. **`VALUES` 不能跟 `WHERE`**：PostgreSQL 的 `INSERT ... VALUES (subquery) WHERE NOT EXISTS(...)` 是语法错误。必须用 CTE + `INSERT...SELECT` 形式。psql dry-run 抓出来的，否则上线即炸。
2. **`t_subject.id` 是 `ALWAYS IDENTITY`**：显式插 id 必须带 `OVERRIDING SYSTEM VALUE`（V102_5 的写法）。
3. **`NOT EXISTS` 守卫不能加 `deleted=0`**：`uq_subject_code_ent(code, enterprise_id)` 是**非部分**唯一索引，不含 deleted 过滤。若存在一条已逻辑删除的 1602 行，带 `deleted=0` 的守卫会放行插入 → 撞唯一约束。

另：`generate-sequence` 端点与"资产分类→费用科目映射"两个事项**有意推到 P84**，理由：
- `generate-sequence` 是 P84 结账工作台的直接依赖，跟工作台一起做可一次改到位
- 费用科目映射是新功能（新增配置入口），不属于 P85 的结转序列修复范围；PRD 原文写"管理费用-折旧"但科目表无该子科目、资产卡片也无映射字段，硬造会引入未经设计的配置面

## 3. BDD 验收标准

### P85-A 性能修复

#### 场景 A1：损益结转只取本期已过账净额非零科目（L2 集成 🟡 数据迁移/聚合 SQL）

```gherkin
- Given t_voucher 有 202607 和 202608 两个期间的 POSTED 凭证，含 6xx 损益科目分录
  And 有一条 6xx 科目本期借=贷（借贷对冲，净额为 0）
  And 有一条非 POSTED 状态的 6xx 凭证
- When 调用 selectProfitSubjectTotals("202608")
- Then 只返回 202608 期间、已过账、净额非零的损益科目
  And 不含 202607 期间数据（负向断言：跨期间不泄漏）
  And 不含借贷对冲科目（负向断言：净额为 0 的不返回）
  And 不含非 POSTED 凭证的分录
```

#### 场景 A2：`generateProfitCarryOver` 行为不回退（L3 Service，S-17 契约）

```gherkin
- Given 期间有损益科目余额
- When 调用 generateProfitCarryOver(period, userId)（签名未变）
- Then 返回凭证 ID，生成的分录与旧实现口径一致
  And 不产生多余的抵消分录（负向断言：净额为 0 科目不生成分录）
```

### P85-B 结账日志

#### 场景 B1：结账/反结账写日志，listCloseLog 可查（L2 集成 🟡 数据迁移）

```gherkin
- Given 期间 202608 处于可结账状态
- When 调用 closePeriod("202608", userId)
- Then t_close_log 新增一条 action=CLOSE 的记录
  And operator_id = userId（operator_id 自定义列落库，不依赖 created_by）
  And result 与 duration_ms 均有值
- When 调用 listCloseLog("202608")
- Then 返回该期间日志，按时间倒序
```

#### 场景 B2：t_close_log 约束与往返（L2 集成 🟡 数据迁移）

```gherkin
- Given t_close_log 已由 V151 建表
- When insert 一条合法日志并 selectById 取回
- Then 所有字段往返一致，operator_id 非空
  And createdAt 由 FieldFill.INSERT 填充
- When insert 一条 result 不在枚举内的记录
- Then 数据库拒绝（chk_close_log_result 生效，负向断言）
- And 按期间查询只返回该期间记录（负向断言：其他期间被排除）
```

#### 场景 B3：日志写入失败不阻断结账（L3 Service）

```gherkin
- Given appendCloseLog 内部抛异常（模拟 DB 故障）
- When 调用 closePeriod
- Then 结账主流程仍然成功（日志写入被 try-catch 吞掉）
```

### P85-C 折旧自动制证

#### 场景 C1：DEPR 凭证借贷平衡、DRAFT、溯源回写（L2 集成 🟡 状态变更/CHECK 约束）

```gherkin
- Given 当期已有 2 条 t_asset_depreciation 记录（金额 1200 + 800）
  And 期间状态 open，科目 6602/1602 已配置
- When 调用 generate("202608", userId)
- Then 返回 voucherNo = "DEPR-202608"
  And totalDebit = totalCredit = 2000.00
  And 凭证状态 = DRAFT（负向断言：绝不自动审核、绝不自动过账）
  And 凭证头 totalDebit 与 totalCredit 相等
  And 分录明细借贷合计相等且各非零（chk_entry_not_both_zero 生效）
  And 两行分录 subject_id 分别指向 6602 和 1602
  And enterprise_id 自动填充（未显式设置）
  And 两条折旧记录的 voucher_id 均回填指向本凭证
```

#### 场景 C2：幂等——重复调用拒绝（L2 集成 🟡 状态变更）

```gherkin
- Given DEPR-202608 已生成
- When 再次调用 generate("202608", userId)
- Then 抛"已存在 1 张折旧凭证"（不静默跳过、不覆盖）
  And 期间内仍只有 1 张 DEPR 凭证（负向断言：不产生第二张）
```

#### 场景 C3：全部前置与数据质量校验失败不产生任何写入（L3 Service + L2 集成）

```gherkin
- Given 期间未配置
- When 调用 generate
- Then 抛"未配置"（负向断言：未 insert 任何凭证）

- Given 期间已结账
- When 调用 generate
- Then 抛"已结账"（负向断言：未 insert 任何凭证，守 P87 期间锁）

- Given 当期无折旧数据
- When 调用 generate
- Then 抛"请先在资产模块计提折旧"（负向断言：不生成空凭证）

- Given 折旧金额为空
- When 调用 generate
- Then 抛异常并指向具体记录 ID

- Given 折旧金额非正
- When 调用 generate
- Then 抛"金额非正"（负向断言：不生成零元/负数凭证）

- Given 科目 6602 或 1602 未配置
- When 调用 generate
- Then 抛"未配置科目"（负向断言：不做降级假设、不跳过制证）
```

#### 场景 C4：计提与制证分离（L3 Service，守铁律#1）

```gherkin
- Given 用户已在资产模块手动计提折旧
- When 调用 generate
- Then 金额完全来自 t_asset_depreciation.depreciation_amount
  And 不出现任何折旧计算逻辑（负向断言：制证不自行算折旧）
  And 不调用 depreciatePeriod
```

## 5. 风险与遗留

1. **`created_by` 全局不落库（既有问题，非 P85 引入）**：`BaseEntity.createdBy` 标 `@TableField(exist=false)`，MyBatis-Plus 不生成该列 INSERT。库里既有的 `CLOSE-202407` 凭证 `created_by` 同样是 NULL——`generateProfitCarryOver` 里的 `setCreatedBy(userId)` 从来没生效过，**所有自动生成凭证的创建人都不可追溯**，审计只靠 `t_close_log.operator_id` 与应用日志。建议单独开工单评估：要么建 `operator_id` 列（同 P85-B 做法），要么给自动生证加统一操作者记录机制。**P85-C 的 `setCreatedBy(userId)` 同样无效，已在 RealDB 测试中断言真实行为（assertNull）并注释说明**，不掩盖。
2. **`generate-sequence` 端点未做**：推到 P84，与结账工作台一起做（理由见 §2）。PRD-017 §接口表里的该端点暂缺。
3. **费用科目映射未做**：PRD 原文"管理费用-折旧"，现行科目表无该子科目、资产卡片无映射字段。P85-C 固定用 6602/1602，不做映射配置。管理用/生产用/销售用设备目前全部计入 6602。
4. **P85-A 性能未做基准对比**：PRD P85-BD2 要求 10 万行 <2s 并与修复前对比。已消除全表扫描与两层 N+1（结构性修复），但**未构造 10 万行数据集实测**——需要专门的性能压测环境。当前只有功能正确性验证。
5. **V130 防御性修复是并行提交引入的问题**：该 migration 引用了未 seed 的科目 code，新容器 Flyway 链会断。已加防御性跳过，但根因在并行提交侧，建议同步给该提交者。
