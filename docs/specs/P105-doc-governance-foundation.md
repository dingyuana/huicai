## 1. 输入契约

| 输入 | 类型 | 约束 |
|---|---|---|
| `REQUIREMENTS_REGISTRY.md` | 需求登记册 | 声称「唯一权威来源」，需先满足编号唯一前提 |
| `docs/specs/*.md` | 100+ SPEC | 状态行必须与代码实况一致 |
| 硬数字 | AGENTS §0 | 作为**唯一可信源**，其余文档引用之 |

## 2. 输出契约

| 输出 | 验收标准 |
|---|---|
| 编号唯一 | 全库 REQ 编号无重复；SPEC 指针全部可解析（无空悬） |
| 状态一致 | 无「标待开发但代码已落地」的 SPEC；无「标规划中但实现完成」的 REQ |
| 硬数字单点 | 注解数/测试类/迁移数/端点数只在 AGENTS §0 记一次，其余引用 |
| 治理文档有效 | `flyway-governance.md` 如实记录版本号缺口与基线决策，规则不再自相矛盾 |

## 3. 状态流转

```
重号/空悬指针 ──> 重新编号/补指针 ──> 编号唯一（可追溯地基）
状态滞后 ──────> 批量回写状态行 ──> 状态=代码实况
硬数字冲突 ────> 收敛到 AGENTS §0 单一来源 ──> 其余引用
治理文档失效 ──> 更新至 V2.0（如实记录缺口）─> 规则与实际一致
```

## 4. 异常处理

| 场景 | 处理 |
|---|---|
| 重新编号破坏外部引用 | 版本变更记录登记映射（旧号→新号），保留追溯 |
| 状态回写误判（以为未实现） | 以 `test_ref` 类/端点是否真实存在为判据，不凭记忆 |
| 硬数字再次漂移 | 纳入提交前 checklist（§2.4），每次 commit 后更新 §0 |

## 6. 竞品对标（铁律 #15）

此 SPEC 属内部工程治理，无直接竞品功能对标；对标的是**工程规范成熟度**：用友/金蝶等成熟产品均以「单一需求库 + 编号唯一 + 文档与代码同步」为基线（SAP 用 ALM 需求管理保证追溯）。本项目文档治理落后于其功能进度，需补平以支撑后续演进。

## 7. 风险与不在范围

- **重新编号**影响追溯 → 版本记录保留新旧映射。
- **不在范围**：AI 相关文档、需求优先级重排（另议）、文档工具化自动校验（可后续加 CI 脚本）。
